# Daily Report Skill

根据项目 git 提交历史生成格式化的工作日报与周报。

## 核心逻辑定义

为了保持日报与周报的一致性，请严格遵守以下字段映射逻辑：

1.  **工作内容 (Project Name)**：
    * 对应 Git 仓库的根目录名称或主要项目名称。
    * 在日报表格中体现为 **"工作内容"**。
    * 在周报表格中体现为 **"任务名称"** 或 **"工作内容"**。

2.  **功能名称 (Feature)**：
    * 对应具体的模块、功能点或 Commit Scope (例如 `feat(auth):` 中的 `auth`)。
    * 需从提交记录中提炼出具体的功能模块。

3.  **任务详细描述 (Task Description)**：
    * **生成原则**：清晰明了，突出重点，提供充足上下文。
    * **禁止**：过于简略（如"修改代码"、"修复bug"、"重构模块"）或过于啰嗦（如粘贴大段代码）。
    * **要求**：描述必须包含以下要素（根据实际情况选择）：
        * **问题背景**：为什么要做这个改动？（解决了什么痛点/问题）
        * **实现方案**：采用了什么技术方案或架构设计？
        * **核心改动**：具体修改了哪些模块、类、函数？
        * **技术细节**：关键的技术点（如算法、协议、数据结构）
        * **效果/价值**：改动后带来什么改进或能力提升？
    * **示例**：
        * *Bad*: "优化数据同步接口"
        * *Good*: "针对数据同步接口响应慢的问题进行优化，采用异步批量处理策略替代原有的逐条同步方式，将接口平均响应时间从 2s 降低至 500ms，提升了系统整体吞吐能力"
        * *Bad*: "添加用户认证功能"
        * *Good*: "实现基于 JWT Token 的用户认证系统，包含登录验证、Token 刷新、权限校验等完整流程。新增 AuthMiddleware 中间件拦截请求，集成 Redis 存储 Token 黑名单，支持单点登录控制"

## 报告生成模板

### 1. 日报格式 (Daily Report)

请按以下格式输出每一项主要变更。如果有多个 commit 属于同一功能，请合并展示。

```markdown
# 工作日报

## 日期：YYYY年MM月DD日

### 【功能/模块名称】
| 项目 | 详情 |
| :--- | :--- |
| **功能名称** | <这里填写具体的功能模块，如：用户登录模块> |
| **工作内容** | <这里填写主要项目名称，如：CRM后台系统> |
| **任务详细描述** | <核心内容。要求清晰明了，突出重点，避免流水账。> |
| **难度** | ⭐⭐⭐ (根据代码复杂度和修改行数自动评估 1-5 星) |
| **作用** | <简述改动带来的效果，如：修复线上崩溃、新增支付渠道> |
| **工作量** | <xx> 行代码变更 |
| **工时算量/h** | <根据工作量估算，每 100 行约 1h，不足 0.5h 按 0.5h 计> |


### 2. 周报格式 (Weekly Report)

请汇总本周（或指定日期范围）的所有工作，生成以下表格。需确保与日报数据一致。

**格式要求**：
1. 表格使用无冒号分隔符：`|序号|任务名称|任务描述|当前进展|完成日期|`
2. 日期格式：`01月19日 周一`（包含星期几）
3. 完成情况：使用 `已完成` 或 `持续推进中`
4. 工时算量：直接填写工时数值（如 `8`），不按代码行数计算
5. 必须包含 `## 三、本周工作小结` 部分，撰写整体总结

```markdown
# 本周工作任务总结（MM月DD日-MM月DD日）

## 一、工作任务概览
*(此表用于概览项目维度的进度，**任务描述必须详细阐述本周期内完成的主要工作内容**)*

**重要说明**：
- "任务描述"字段需要从本周所有提交中提炼出**整体目标和核心成果**
- 不能简单写"进行中"或"完成开发"，必须写清楚**完成了什么**
- 需要包含：主要模块/功能、技术方案、解决的问题、达成的效果

|序号|任务名称|任务描述|当前进展|完成日期|
|---|---|---|---|---|
|1|<任务编号（如：HD-HDAI-202501）>|<详细描述：本周完成了XX系统的重构与优化，包括模块1的XXX功能实现、模块2的XXX问题修复，解决了XXX痛点，达成了XXX目标>|持续推进中/已完成|持续迭代/YYYY/MM/DD|

## 二、本周个人任务执行情况
*(此表为详细的工作流水，按日期汇总当日工作)*

|日期|工作内容|任务详细描述|完成情况|工时算量/h|
|---|---|---|---|---|
|01月19日 周一|任务编号1、任务编号2|1. 任务1：...；2. 任务2：...|已完成|8|
|01月20日 周二|任务编号1、任务编号2|1. 任务1：...；2. 任务2：...|已完成|8|

## 三、本周工作小结

<撰写整体总结：本周核心聚焦XXX工作，完成了XXX模块的开发与优化，解决了XXX问题。后续将重点推进XXX工作。>
```

## AI 处理策略 (Internal Instructions)

1.  **数据获取**：
    * 优先读取 `git log --stat` 和 `git diff --shortstat`。
    * 若 commit message 包含 Jira/Issue ID，提取作为补充信息。

2.  **内容清洗与生成**：
    * 忽略 `merge branch`、`typo`、`format` 等无实际业务含义的提交，除非涉及大量代码变动。
    * **描述优化**：将技术语言转化为业务语言。
        * *Bad*: "Updated UserDAO.java for SQL injection fix"
        * *Good*: "修复用户数据层潜在的安全漏洞，增强SQL查询安全性"

3.  **难度与工时评估标准**：
    * **⭐ (1星)**: 简单的配置修改、文案修改 (< 20 行)。
    * **⭐⭐ (2星)**: 普通的 CRUD 逻辑、Bug 修复 (20-100 行)。
    * **⭐⭐⭐ (3星)**: 新功能开发、涉及多个文件的逻辑修改 (100-300 行)。
    * **⭐⭐⭐⭐ (4星)**: 核心架构调整、复杂算法实现 (> 300 行)。
    * **⭐⭐⭐⭐⭐ (5星)**: 重大重构、底层内核修改。

4.  **兜底规则**：
    * 如果在 Git 根目录下无法判断“项目名称”，默认使用当前文件夹名称。
    * 如果缺少具体时间，默认生成“昨天”和“今天”的日报。
